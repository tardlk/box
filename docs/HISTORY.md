## 2. 2026-10-29 新增豆瓣导航

> 收口状态：用户已在 FongMi 5.8.4 上确认「点卡片进入搜索页、自己选源」可用。关键是配置里的 `indexs: 1`（见 10.2），
> 代码侧无需再改；手机版进 `SearchActivity`，电视版进 `CollectActivity`。


用户要求在参考实现 `lushunming/AndroidCatVodSpider` 的 `Douban.java` 基础上加豆瓣导航。实现见 `Douban.java`，说明见 [DOUBAN.md](../DOUBAN.md)。

接手时要先知道的四件事：

1. **`msearch:` 是宿主约定，不是本项目发明**。`VodPlaybackController.checkId` 遇到 `msearch:` 前缀直接 `detailEmpty(false)`，不请求详情。
   **前缀后面必须跟片名**（`msearch:老友记 第一季`）：仓库所有者另一个 JS 脚本这样写，真机进入搜索流程；放豆瓣数字 ID 会直接开播第一个同名结果。
   当前宿主分支只用前缀、不解析后缀，所以别以本地读到的源码为唯一依据——以真机行为为准。
   同理 `detailContent` 返回 `{"list":[]}` 且**不带 `msg`**，否则 `detailEmpty(hasMsg())` 会把空详情当最终结果。
2. **`searchable` 必须是 0**。否则搜索结果还是 `msearch:` 卡片，点进去又触发搜索，绕回自己。
   参考实现同样设为 0（`json/index.json` 的「豆瓣仅推荐」）。
3. **接口只认微信小程序 UA**。同一 `apikey` 配 Chrome UA 稳定返回 HTTP 400 / `code 997`；交替实测确认过。
   不能把 `Douban.UA` 换成通用的 `SiteHttp.UA`，因此 `SiteHttp.open` 增加了带 UA 的重载——这是本次唯一改动的共用代码。
4. **封面是直连地址加 `@Referer=` 后缀**，由宿主 `ImgUtil.getUrl` 解析出请求头再加载，不要改回走 `Proxy`。
   2026-10-29 曾误判「封面必须带 `Accept: image/*`」，已更正：那些 418 是连续请求触发的 IP 级限流，不是缺头。

第一版把封面接到了 `Proxy` 上，并为此抽出 `Proxy.url`、把 `Ikanbot.image` 改成调用它。设备上看不到豆瓣封面后已整体还原：
`Proxy.java`、`Ikanbot.java` 与加豆瓣之前逐字节一致，豆瓣改为直连 URL。加这个站点最终只新增 `Douban.java` 和一处 `SiteHttp` 重载。

关于「点卡片没有选源」：第一版把 `msearch:` 后面写成豆瓣数字 ID，真机点开直接播了第一个同名结果。
仓库所有者指出他另一个 JS 脚本能把点击变成搜索，对照后差别就在后缀——JS 写的是 `msearch:` + **片名**。
现已照此对齐，并同步去掉 `detailContent` 的 `msg`。以后遇到「点卡片行为不对」，先比对这个脚本的约定，
不要只根据本地宿主源码下结论：当前分支不解析后缀，但真机行为说明宿主链路里还有别处在用这段内容。

### 2.1 点卡片进搜索页靠的是 `indexs: 1`

宿主用 `Site.isIndex()`（即配置里 `indexs == 1`）区分「导航站」：手机版点卡片走 `SearchActivity`，
电视版走 `CollectActivity`（都带 keyword）；没有这个字段就直接 `VideoActivity` 并自动播第一个同名结果。
2026-10-29 在 Android TV 模拟器 + FongMi 5.8.4 上做了三组对照（我们的 JAR / 仓库所有者的 JS / 其 39 站完整配置），
行为差异全部由这个字段解释。**配置里删掉 `indexs` 就会退回“点一下就播”。**

分类设计上把剧集筛选与综艺筛选拆成两个分类：豆瓣的 `tags` 之间是「与」关系，
电视剧形式与综艺形式放在同一组会互相冲突，选两个就查不到东西。

验证：当时 75 项契约检查（30 + 17 + 28）全过；`--douban` 七个分类各 20 条、榜单 10 条、Top250 第二页、封面 270x405 直连成功。
（爱看机器人提速后契约增至 35 项，全库现为 80 项。）
卡片点击与选源已由仓库所有者在 FongMi 5.8.4 上确认；仍未确认的是跨站搜索结果聚合与遥控器操作。

`package.py` 的 `sites` 顺序即首页 Tab 顺序，第一个是默认页。2026-10-29 按仓库所有者要求把 `douban` 调到第一，
次序为 `douban`、`ikanbot_fresh`、`ivdy`。这次只改配置，没有重新打包 JAR，线上 MD5 仍是 `4c420eb0…`。

注意：豆瓣 `searchable=0`，所以点卡片后的同名搜索不会把豆瓣算进去，自动选中哪个来源仍由 `ikanbot_fresh`、`ivdy` 的相对顺序决定；

## 3. 2026-10-29 爱看机器人提速

用户反馈同一个站，仓库所有者的 drpy3 源（`爱看机器人.js`）明显比我们的 Java 快。对比后按四处结构差异改：

1. **加缓存**：首页/分类/搜索 180 秒、详情 120 秒。此前完全没有缓存，每次切 Tab、每次回看都重拉整页。
   实测详情首次 9.3 秒、**命中缓存 0 毫秒**。
2. **封面改走站点自己的封面代理** `imgp2.ikanbot.eu.org/i/<ID>?u=<base64url>`，与 JS 源一致。
   之前每张封面都要「客户端 → 本插件代理 → 源站」绕一圈，一页 24 张就是 24 次多余往返；
   而且 `Proxy.proxy` 每张图都做一次 DNS 校验、`image()` 每张卡片做一次反射。`i` 只是缓存名，传任意数字都行。
   **本节已被 §14 取代**：该代理是境外 Worker，实测单张 4–40 秒且约一半不响应，现已改为豆瓣直连 + `@Referer=`。
   保留这段是为了说明「当时为什么这么改」，不要按它回退。
3. **WebView 降级从 90 秒收到 25 秒**。直连失败时会开 WebView，90 秒等于让用户干等一分半。
4. **入口域名保持 `v.ikanbot.com`**。曾试图直连 `www.ikanbot.com` 省一次 301，实测 www 的详情页直接超时，
   而 `v` 会 301 到可用的 www1。`SiteHttp` 跟随一次后把 `origin` 更新成落地域名，后续不再吃 301。**不要改成 www。**

`PosterTest` 已改为检查站点封面代理这条真实链路（10 季全部返回可解码 JPEG）。
未做：搜索翻页仍靠 `next` 游标（JS 用 `?p=N` 直达，但实测该参数返回空页，没敢用）。
遗留：15 秒读超时在该站抽风时会直接报错；若长期如此需要单独评估是否放宽。

## 5. 2026-10-29 16:20 封面被 403 的修复

用户反馈「爱看机器人加载慢、没有封面」。慢是链路问题（见 4.2），**没有封面是代码问题**，已在 Android TV 模拟器上复现并修复。

### 5.1 根因

站点封面代理 `imgp2.ikanbot.eu.org` 拒绝裸图片请求。同一张图、同一个 URL，只换请求头：

| 请求头 | 结果 |
|---|---|
| 无 | 403（HTML 错误页 4551 字节） |
| 仅 UA | 403 |
| 仅 Referer | 403（3 次） |
| UA + Referer | 200，28036 字节真 JPEG，270×381 |

宿主的图片加载器裸请求，所以封面必然 403。这不是「加载慢」。
第 3 节把封面从本插件代理改走站点代理时，只用 `PosterTest`（Java 请求自带 UA/Referer）验证过，
**从未验证真机图床的请求形态**，这就是缺口。

### 5.2 修复

`Ikanbot.poster()` 给站点代理地址追加宿主认识的请求头后缀，与 `Douban.java` 同一个机制：

```text
https://imgp2.ikanbot.eu.org/i/<ID>?u=<base64url>@Referer=https://v.ikanbot.com/@User-Agent=Mozilla/...
```

宿主 `ImgUtil` 会取出 `@Referer=` / `@User-Agent=` 作为请求头，再 `split("@")[0]` 剥掉后缀，
所以**客户端仍然直连 CDN，没有多一跳**——`§11` 的性能收益保留。
注意 `u` 的 base64url 不含 `@`，加后缀不会破坏参数。

**不要删这两个后缀**，删了封面会静默退回全空（403 不报错，只是没图）。

### 5.3 证据

同一台 `boxtest`（Android TV 1080p）模拟器，同一批豆瓣热门内容：

| 设备上的 jar | 封面 |
|---|---|
| `7c6bf0b2…`（改前） | 0 张真图，全部空框 |
| `bbb580fd…`（改后） | `黑球`、`死神 千年血战篇` 等真剧照出现 |

设备 `cache/jar/` 里两个文件的 MD5 可对照，不是靠肉眼判断。
其余仍偶发空白的卡片受 4.2 的链路抖动影响，与本修复无关。

发布后又在同一台模拟器上跑了一次**线上配置**（`config_0` 指向 gh-proxy 的 `main/config.json`）：
设备最终加载的 JAR MD5 = `91c19c17…`，与线上一致；爱看机器人电影分类首屏 10 张卡片里 8 张显示真实海报，
另 2 张是宿主图床的失败占位。同一段代码多数成功，说明请求头路径已生效，剩下的是单张图超时。

契约检查由 80 项增至 **81 项**（新增「封面附带站点代理要求的 Referer 与 UA 后缀」）。

- 仍未在真机（真实电视盒子）确认，只有 Android TV 模拟器。

## 6. 2026-10-29 16:50 封面改回豆瓣直连（覆盖第 3 节的做法）

§13 补上请求头后封面能显示了，但用户仍反馈「还有看不到封面的」。继续查，问题不在豆瓣，在站点那个封面代理。

### 6.1 实测：慢和失败都来自 imgp2

同一批封面、同一时段：

| 取图路径 | 结果 |
|---|---|
| `imgp2.ikanbot.eu.org`（站点代理） | 单张 4–40 秒；连续 4 次请求里 2 次完全不响应（40 秒零字节） |
| 豆瓣 CDN 直连 + Referer | 连续 12 张 **12/12 成功**，每张 0.10–0.43 秒，全部 200 |

豆瓣图床的最小请求头（同一 URL 只改头）：

| 请求头 | 结果 |
|---|---|
| 无 | **418** |
| 仅 UA | **418** |
| 仅 Referer | **200**，0.11 秒 |

`imgp2` 是境外 Cloudflare Worker，路径是「客户端 → 出境 → 回到豆瓣 CDN」，慢和偶发无响应都是这一跳造成的；
客户端图床超时后就会显示失败占位，看起来就是「没封面」。

### 6.2 顺带纠正一处文档错误

`DEVELOPMENT.md` 原先写「`i` 只是缓存名，服务端只认 `u`」。实测相反：**`i` 是缓存键**。
用「杯雪的 `i` + 黑球的 `u`」请求，返回的是杯雪的图（73008 字节），而用随机 `i` + 黑球的 `u` 才返回黑球的图（26355 字节，MD5 与豆瓣源一致）。
所以想靠把 `m_ratio_poster` 换成 `s_ratio_poster` 拿小图是无效的——命中缓存后服务端直接吐大图。这条也解释了为什么只能换路径、不能换尺寸。

### 6.3 改动

`Ikanbot.poster()` 对豆瓣域名的封面**直连豆瓣 CDN**，只追加 `@Referer=https://movie.douban.com/`；
非豆瓣域名仍走本插件代理。这与 `Douban.java` 完全一致，不再经过 `imgp2`。
`posterId()` 与 `imgp2` 拼接逻辑一并删除（不再有人用），契约测试相应改写：
80 项（爱看机器人 35 + 爱电影 17 + 豆瓣 28），新增「直连 + Referer」「旧版路径先修正再补 Referer」「非豆瓣不受影响」。

### 6.4 设备验证

**仓库所有者已在手机上使用最新配置，反馈「ikanbot 正常了」**（2026-10-29 16:50）。这是本次改动的最终验收依据。

模拟器这边因为站点 HTML 正在抽风没能复现（宿主直接 `curl` 分类页 3 次只成 1 次，成功 9.5 秒、另两次 35 秒超时；
模拟器里分类请求返回 `爱看机器人：Read timed out` / `timeout`，页面「Nothing here」），
同一时刻豆瓣图床稳定 0.29 秒，所以上面的测量结论仍然成立，只是没能在模拟器里"看着它加载"。

未取样：手机上封面加载的具体耗时、一页 24 张里全部出图的比例。若之后仍偶发空白，按 6.1 的方法对照即可。

## 7. 2026-10-29 17:20 入口域名从 v（跳 www1）改为 www

### 7.1 起因

仓库所有者报告手机上爱看机器人「一直转圈」。他用 Edge 打开 `https://www.ikanbot.com/` 正常，
但打开 `https://www1.ikanbot.com/` **特别慢**。

而插件当时的入口是 `https://v.ikanbot.com`，它 301 到 `www1.ikanbot.com`——也就是说插件正好落在那个慢镜像上。
这一步是第 3 节定下的，但当时的判断基于**本机网络**（那时本机 www 超时、www1 可用），
换个网络就完全相反。写死的单一镜像等于把某个网络的偶然结果当成普遍事实。

### 7.2 实测

本机（经本地代理）：

| 目标 | 结果 |
|---|---|
| `www` 首页 | 3 次里 2 次 200（6.5 秒 / 20 秒截断），1 次无响应 |
| `www1` 首页 | 3 次 200 但正文常在 12–20 秒处被截断 |
| `www` 详情 `/play/390655` | 3/3 通过，15210 字节，`current_id`/`e_token`/`mtype`/`get_tks` 字段齐全 |
| `v` 跳转目标 | 连续 5 次都是 `www1`，跳转稳定但没有意义——稳定地跳到慢的那台 |

顺带否掉一个假设：按 HTTP/1.1 与 HTTP/2 分别请求，两者都会卡（1.1：4 次里 1 次完整；2：4 次里 3 次完整），
所以不是「Java 只支持 1.1」造成的，是这条链路本身不稳。

用同一批请求跑 JS 参考源（`爱看机器人.js`，`HOST` 写死 www、超时 6.5 秒）：
首页超时失败、分类 2.0 秒 24 条、搜索 2.6 秒 10 条。
它比插件更容易失败，恰恰因为超时短；但它的 `HOST` 选择是对的。

### 7.3 改动

`SiteHttp.ROOT` 改为 `https://www.ikanbot.com`。仍然跟随一次跳转并把落地域名记进 `origin`，
万一 www 哪天也开始 301 不至于打回原形。`siteHost` 继续接受 `v` / `www` / `www1` 等写法。

### 7.4 验证

- 契约检查 80 项通过。
- `--live` 在 www 上连跑三轮：**首页与分类第二页 3/3 通过**；搜索两页偶发 `Read timed out`（本机链路抖动，见 4.2）。
- 所有者的网络里 www 本身是快的，因此这次改动对他的实际收益比本机测试体现的更大。

### 7.5 遗留

单一写死域名终究是脆的：这次把方向反过来，下次还可能反过来。
真正的解法是入口探测——同时问几个候选域名、用先答上来的那个，并把结果缓存。
本轮没做，因为它会在冷启动多一次请求；等出现第三次同类问题再上。

## 8. 2026-10-30 暂停启用爱看机器人（未定位原因）

### 8.1 决定

仓库所有者反馈：把入口改成 `www` 之后，手机上仍然「一直转圈」。
在多次尝试后他选择暂时放弃这个站点，配置里移除、代码保留。

### 8.2 我们查到哪一步

| 事实 | 依据 |
|---|---|
| 站点本身活着 | 所有者在 Edge 里能打开 `https://www.ikanbot.com/` |
| 本机能跑通 | `--live` 三轮里首页与分类第二页 3/3 通过；详情 3/3、字段齐全；`--posters` 10/10 |
| 换成 www 后仍失败 | 所有者手机实测，2026-10-30 凌晨 |

### 8.3 没拿到的关键信息

缺了这行错误，就无法区分：超时、Cloudflare 拦截（Java 的 TLS 指纹与浏览器不同）、
DNS 卡住、还是宿主根本没把请求发出去。

本机所有测量都经过一个不稳的本地代理（HISTORY 4.2），**从来没有过一条干净的链路**，
所以这一路的判断都建立在不稳的地基上——包括「www 比 www1 快」这个结论，对所有者成立、对本机不成立。

### 8.4 下次重启这个站点时该怎么做

1. 先要一句真实的错误文本。FongMi 设置里有调试日志，或在手机上抓一次 `adb logcat | grep -i catvod`。
2. 不要在代理链路上做「哪个域名快」的判断，用所有者自己的网络测。
3. 怀疑 Cloudflare 按 TLS 指纹/UA 拦截时，用同样的 UA 和 TLS 参数从浏览器复现，再对比 Java 的请求。
4. 恢复步骤：`scripts/package.py` 里那段被注释的站点定义放回 `sites` 列表，
   `scripts/verify_release.py` 的 `REQUIRED_APIS` 加回 `'csp_Ikanbot'`，然后走一次配置发布（JAR 不用重打）。

## 9. 2026-10-30 根因：给站点请求带 Referer 会被 Cloudflare 拦成 403

第 8 节暂停站点之后，仓库所有者装了 BlueStacks Air 继续排查。
在 Android 13 的真实运行环境里终于拿到了一直缺的那条错误。

### 9.1 怎么找到的

BlueStacks 上：豆瓣导航与爱电影正常，爱看机器人的**首页 24 条、海报全出**，但点进详情触发了 WebView 兜底，
日志里是 `{"list":[],"url":"","msg":"爱看机器人：null"}` —— 一个 message 为 null 的异常。
先把 `error()` 改成「没有 message 时输出异常类型」，再回头查直接请求那一步，桌面探针给出：

```
站点要求网页验证（HTTP 403）
```

而同一秒、同一 IP 用 curl 请求同一个 URL 是 **200**。于是逐组加头对照：

| 请求头 | 结果 |
|---|---|
| 只带 UA | **3/3 200** |
| UA + `Accept-Encoding: gzip` | **3/3 200** |
| UA + `Referer: https://www.ikanbot.com/` | **0/3，全 403** |
| UA + Referer + gzip（就是我们当时的实现） | **0/3，全 403** |
| 再加浏览器 `Accept`、`Accept-Language` | **仍然 403** |

**只要带上站点自己的 Referer，就必被拦。** 用 `SiteHttp` 连打 6 次验证：改前 6/6 全是 403，改后 6/6 全部 200。

参考实现 `爱看机器人.js` 里那句 `Referer: null` 的注释（"null 避免 drpy3 自动补入 Referer"）原来就是这个意思，
它在 `play` 里才给媒体请求补 Referer。这一条我们没照做，`SiteHttp.get()` 一直在发 `Referer: origin + "/"`。

### 9.2 改动

- `SiteHttp.get()` 不再给站点请求设 Referer；`open(url, referer)` 在 referer 为空时跳过该头。
  播放请求（`playerContent` 返回的 header）照旧带 Referer，不受影响。
- `Ikanbot.error()`：异常没有 message 时输出异常类型，不再显示"爱看机器人：null"这种废话。

契约检查 80 项通过；`directDetail("1023899")` 返回 28 条线路与真实 m3u8；
`--posters` 仍是 10/10。

### 9.3 为什么绕了这么久

第 4、7 节所有结论都建立在「本机经本地代理的链路」上，那条链路本身不稳，
403 和超时混在一起，被当成同一个"站点抽风"。真正把问题分开的是一次干净的对照：
**同一 URL、同一秒、只改请求头**。以后遇到"站点有时打得开有时打不开"，先做这个对照，不要先怀疑网络。

## 10. 2026-10-30 10:15 端到端验收（BlueStacks / Android 13）

### 10.1 环境与方法

BlueStacks Air（Android 13、arm64-v8a、手机版影视 5.8.4）。这台机器**没有 root**，
`su` 与 `run-as` 都不可用，所以配置只能用界面输入。

一个绕不开的坑：这个应用会自行给输入框补 scheme——`input text 'https'` 落进去是 `http://ttps`。
试过禁用输入法（`ime disable`）也一样，说明不是输入法的自动更正，是应用自己的逻辑。
**规律是「首字符 h 被吃掉、前面补 http://」**，于是改成直接输 `h192.168.5.6:8899/config.json`，
落进去正好是 `http://192.168.5.6:8899/config.json`。

为了不动发布产物，本地只做了一件无害的事：把仓库里已发布的
`jar/box-5d4df9465d4ec35bc519dcc83d1a9f50.jar` 原样拷到 `/tmp/bsstage`，
配一份 spider 指向 `./box-5d4df946…jar` 的 config。**测的就是发布出去的那个 JAR 字节**，
不是临时构建。

### 10.2 结果：整条链路通

| 环节 | 结果 |
|---|---|
| 配置加载 | `GET /config.json` + `GET /box-5d4df946….jar` 均 200；第三次启动只取 config（md5 命中，不重下） |
| 首页 | `page=1, pagecount=1, limit=24`，24 条，封面全是 `img9.doubanio.com` 直连 |
| 详情 | `directDetail` 成功，**没有触发 WebView 兜底**，8 条线路 |
| 取址 | `{"parse":0,"url":"https://play.xluuss.com/play/egJxGgGd/index.m3u8",...}` |
| 播放 | 点「正片」后正常出画面（西班牙片《黑球》的片头字幕） |

修复前，同一台机器上是「首页正常、点详情进 WebView 兜底、`msg` 为空」。
现在这条路径上没有兜底、没有异常，`Referer` 去掉就是分水岭。

### 10.3 顺带发现的一个静默故障模式

排查过程中配置一度指向 `config-20261029-www-entry.json`，而那份快照在 2026-10-30 的清理里被删了。
表现是**首页空白、不报错**，日志里只有：

```
com.google.gson.JsonSyntaxException: MalformedJsonException: ... at line 1 column 5
java.lang.IllegalArgumentException: Expected URL scheme 'http' or 'https' but no scheme was found
```

也就是「404 → 返回 HTML → 被当 JSON 解析 → 配置为空」。用户看到的就是"没有内容"。
所以清理历史快照有代价：**任何人存了旧快照地址，配置会静默失效**。
对外应始终给 `config.json`（永远存在），快照只用于回滚与临时对照。
